# 패킷 제너레이터 — 요구사항 정의서 (초안)

작성일: 2026-07-30 · 상태: 초안 (대화 기반) · 방향: **B안 (C + DPDK 직접 개발)**

---

## 1. 한 줄 요약

L2~L7 헤더를 자유롭게 조립한 패킷을 특정 IP/URL로 **고속(NIC당 100G) 전송**하고,
비정상 handshake를 포함한 프로토콜 동작을 **테스트·검증**하는 리눅스 기반 도구.

## 2. 배경 / 목적

- 본인이 관리·테스트 권한을 가진 장비를 대상으로 한 **연동 검증 / 부하 테스트 / 프로토콜 이상동작(fuzzing) 테스트**.
- 커널 TCP 스택이 자동으로 처리하는 handshake를 **직접 통제**해야 하므로(예: ACK 의도적 생략), 일반 소켓 API로는 불가능 → 커널 우회 접근 필요.

> ⚠️ 전제: 대상은 항상 **본인 소유/테스트 승인된 장비**. 제3자 IP 대상 트래픽 생성은 범위 밖.

## 3. 확정된 요구사항 (대화 정리)

**환경**
- 실행 OS: **Ubuntu 26.04 LTS (커널 7.0)** — Azure MANA 커널 6.14+ 요건 충족, 3대 클라우드 공식 이미지·DPDK 패키징 지원
- GUI 필요 (CLI 단독 아님)
- **실행 형태 2종을 모두 지원**: ① Docker Compose(정본), ② **컨테이너 없이 장비
  안에서 직접 실행(단독 실행)**. 바이너리와 채널 구조는 같다 → 4-3 절
- **장비 2대 이상을 한 제어부가 묶어 구동**한다 → 4-3-4 절

**패킷 조립 (레이어별 완전 커스텀)**
- L2: MAC 주소, VLAN 태그 등 직접 설정
- L3: IP 헤더 (src/dst, TTL, flags, 필요 시 src 스푸핑).
  **IPv4 · IPv6 모두 지원 범위에 포함**한다. 성능 기준 프레임은 더 가혹한
  IPv4(64B)로 잡되, 헤더 빌더·판정 규칙·PCAP 재현은 양쪽을 다뤄야 한다
  (IPv6 는 헤더 40B·확장헤더 체인·checksum 부재 등 IPv4 와 구조가 다르다) → 3절 성능
- L4: TCP/UDP — 포트, 플래그(SYN/ACK/RST/FIN…), 시퀀스/ACK 번호 직접 지정
- L7: **HTTP 및 HTTPS 지원**, 커스텀 페이로드
  - HTTPS는 **정상 TLS 핸드셰이크를 맺은 뒤** 그 위에 요청/커스텀 페이로드 전송

**Handshake 제어 (프로젝트 핵심)**
- 핸드셰이크 과정에 직접 개입 — 예: **ACK를 의도적으로 보내지 않음**, 순서 변경, 비정상 플래그 조합 등

**성능**

**보장 단위는 PF(NIC 포트) 하나의 line rate 다.** 지원 속도는 **1G / 10G / 100G**,
PF 개수 **N 은 장비가 허용하는 만큼 확장**되는 구조이며 총 대역은 `PF 라인레이트 × N`
이다. "400G" 는 목표기의 기준 구성(100G × 4)을 가리키는 것이지 아키텍처 상한이 아니다.

이 구조는 이미 배포 계층에 반영돼 있다 — **PF 하나당 데이터플레인 인스턴스 하나**이고
(4-3 절), N 은 장비에 꽂힌 PF 개수로 결정된다. 장비를 여러 대 두면 N 은 그 합이다.
따라서 NIC 을 늘리는 데 코드 변경은 필요 없고, 아래 세 값만 함께 커진다.

```
코어      N × (인스턴스당 cpuset 크기) ≤ isolcpus 범위      (장비별로)
hugepage  N × MIR_MEM_MB           ≤ hugepages= 예약량  (장비별로)
PCIe      N × x16 슬롯          ≤ 섀시 슬롯 수
```

- **PF 속도별 라인레이트** (기준 프레임 64B, 슬롯 84B)

  | PF 속도 | 64B 라인레이트 (PF 1개) | PMD | 대표 NIC |
  |---|---|---|---|
  | **1G** | **1.49 Mpps** | `igb` | Intel I210 |
  | **10G** | **14.88 Mpps** | `i40e` | Intel X710 — 검증기 |
  | **100G** | **148.81 Mpps** | `ice` | Intel E810 — 목표기 |

- **N 확장 시 총 대역** (`PF 라인레이트 × N`)

  | 구성 | 총 대역 | 총 pps | 위치 |
  |---|---|---|---|
  | 10G × 4 | 40G | 59.52 Mpps | 검증기 (현재) |
  | **100G × 4** | **400G** | **595.24 Mpps** | 목표기 (Phase 7 기준 구성) |
  | 100G × N | N × 100G | N × 148.81 Mpps | 일반형 |

- **기준 프레임 = ETH + IPv4 + TCP 최소 헤더 구성 → 64B** (확정).
  이 기준이 서버 코어 수를 결정한다.

  **왜 64B인가** — 헤더 합은 54B 밖에 안 되지만, IEEE 802.3 최소 프레임이
  64B(FCS 포함)라서 **패딩 6B 가 강제**된다. 즉 L4 까지 최소 헤더만 담은 TCP
  패킷의 선로상 크기는 정확히 64B 이고, 이보다 작은 프레임은 존재할 수 없다.

  ```
  Ethernet header  14B  (dst 6 + src 6 + ethertype 2)
  IPv4 header      20B  (옵션 없음)
  TCP header       20B  (옵션 없음)
                  ────
                   54B
  FCS              +4B  →  58B   ← 64B 에 6B 미달
  패딩             +6B  →  64B   ← 실제 전송 프레임
  ```

  pps 는 프레임에 **preamble 7 + SFD 1 + IFG 12 = 20B** 를 더한 슬롯으로 계산한다.
  위 라인레이트 표가 전부 이 식에서 나온다:

  ```
  pps = 회선속도(bps) / ((프레임 + 20) × 8)

    1G  →   1e9 / (84×8) =   1.49 Mpps
   10G  →  10e9 / (84×8) =  14.88 Mpps
  100G  → 100e9 / (84×8) = 148.81 Mpps
  ```

  **다른 헤더 구성의 최소 프레임** — 성능 목표의 기준은 위 IPv4 구성이지만,
  IPv6 도 테스트 범위에 포함되므로(2절 L3) 함께 기록해 둔다.

  | 구성 | 헤더 합 | +FCS | 패딩 | 프레임 | 슬롯 | 100G | 400G |
  |---|---|---|---|---|---|---|---|
  | ETH + **IPv4** + TCP ← **기준** | 54 | 58 | +6 | **64B** | 84 | 148.81 Mpps | **595.24 Mpps** |
  | ETH + **IPv6** + TCP | 74 | 78 | 0 | **78B** | 98 | 127.55 Mpps | 510.20 Mpps |
  | ETH + VLAN + IPv4 + TCP | 58 | 62 | +2 | **64B** | 84 | 148.81 Mpps | 595.24 Mpps |
  | ETH + IPv4 + UDP | 42 | 46 | +18 | **64B** | 84 | 148.81 Mpps | 595.24 Mpps |

  > IPv6 는 헤더 40B 라 패딩 없이 78B 가 최소이고, 같은 400G 에서 pps 가 **약 14%
  > 낮다**. 성능 기준을 IPv4 로 잡는다는 것은 **가장 가혹한 쪽을 기준으로 삼는다**는
  > 뜻이므로, IPv6 라인레이트는 자동으로 충족된다.

- 현재 개발·검증기(10.10.40.121)는 **X710 4×10G = 40G 상한**이다. 목표의 1/10
  스케일이지만 **PF 4개 = 인스턴스 4개**라 배치 구조가 400G 구성과 동일하므로,
  코드는 `i40e`→`ice` PMD 교체만으로 이식된다. 7절 Open Issue 2 참조.

**결과 확인 (3층위)**
- ① 송신 계층: 실제 전송 바이트, **pps 카운터**, 커널/드라이버 에러
- ② 응답 캡처: 커널 스택 우회이므로 **앱이 직접 수신 패킷을 캡처·해석** (RTT, 응답 플래그, 재전송 여부 등)
- ③ 판정: 규칙 기반 (예: SYN→SYN-ACK 없으면 FAIL, RST면 포트 닫힘)

## 4. 아키텍처 방향 (B안)

| 구성 | 기술 | 이유 |
|---|---|---|
| 패킷 전송 엔진 (데이터플레인) | **C + DPDK** | 100G line rate는 커널 우회(DPDK)가 사실상 유일한 길 |
| 제어·시나리오·집계·판정 | **Go** | 고루틴/채널이 고속 텔레메트리 스트림→GUI push에 적합, 정적 타입, 단일 바이너리 |
| GUI 프론트 | **React + TypeScript** | 워크플로우/시나리오 빌더에 React Flow(@xyflow/react) 활용, 정적 타입 |
| 실시간 차트 | **uPlot / WebGL** | 고빈도 업데이트는 React 리렌더 밖(canvas)에서 렌더링해 병목 회피 |
| 패키징 | **단일 Go 바이너리** (React 빌드를 `go:embed`로 내장) | 실행파일 하나로 배포, 내장 HTTP/WebSocket 서버가 UI 서빙 → 브라우저 접속. 헤드리스 100G 서버에 적합 |

**프로세스 분리 (중요)**: Go에서 cgo로 DPDK 직접 호출은 오버헤드로 비추천.
C 데이터플레인과 Go 제어부를 **별도 프로세스**로 두고 아래처럼 연결한다.

```
[C 데이터플레인 (DPDK)]
   ↑ hugepage 공유메모리 ring / unix socket (제어·텔레메트리)
[Go 제어부]
   ↑ WebSocket
[React + TS GUI]
```

**판정 위치 분리**:
- 마이크로초 단위 실시간 반응(ACK 생략, SYN-ACK 즉시 판정) → **C 데이터플레인**
- 세션 단위 집계·룰 판정·시나리오 오케스트레이션 → **Go**

## 4-2. 설계안 (초안)

### 4-2-1. 설계 원칙
- **분리된 제어/데이터플레인**: 고속 패킷 송수신은 C/DPDK가 담당하고, 시나리오/규칙/GUI는 Go/React가 담당한다.
- **모드 기반 설계**: 상태 없는 고속 모드와 상태 있는 세션 모드로 분리해 각각의 병목을 독립적으로 최적화한다.
- **환경 추상화**: NIC/클라우드/PMD 차이를 백엔드 인터페이스로 감춘다.
- **실시간 가시성**: 송신 카운터, 응답 패킷, 판정 결과를 즉시 UI로 전달한다.

### 4-2-2. 시스템 구성

```text
[React + TypeScript GUI]
        │ WebSocket / REST
        ▼
[제어부 — mir-control (Go), 함대 전체에 하나]
  - 시나리오 엔진 / 규칙 엔진 / 상태 머신
  - 텔레메트리 집계
  - 백엔드 선택/환경 감지
  - 함대 관측 (기대 설정 vs 실측 HelloResponse 대조)
        │ ④ gRPC (스트리밍)
        ▼
[데이터플레인 인스턴스 × N — NIC PF 하나당 하나, 장비 여러 대에 걸쳐도 된다]
  ├─ agent (Go 사이드카)   ── ③ unix socket ──┐   공유 풀 코어
  └─ dataplane (C/DPDK)  ◀───────────────────┘   배타 코어
       - NIC bind / 패킷 빌더 / TX/RX 루프
       - 실시간 판정 / 응답 캡처
```

**채널 번호는 4-2-4 및 `proto/dataplane.proto` 와 일치한다.**
위 그림은 Compose 배포(D 형태) 기준이다. 컨테이너 없이 도는 단독 실행(S 형태)에서는
사이드카와 ④ gRPC 홉이 빠지고 제어부가 ③ 에 직접 붙는다 → 4-3-5 절.

### 4-2-3. 모듈 분해
- **C 데이터플레인**
  - NIC 초기화, 메모리 풀, TX/RX 큐, 패킷 빌더, 헤더 조립, mbuf 관리
  - L2~L4 stateless 전송
  - 실시간 판정(예: SYN-ACK 수신 여부, RST 감지)
- **Go 제어부**
  - 시나리오 실행기, 세션 상태 머신, 패킷 규칙 엔진
  - 텔레메트리 수집 및 UI push
  - 백엔드별 설정 분기
- **React GUI**
  - 시나리오 빌더(노드/엣지 기반)
  - 전송 설정, 패킷 템플릿, 규칙 편집
  - 실시간 차트, 패킷 로그, 세션 상태 패널

### 4-2-4. 주요 인터페이스

논리 채널은 셋이다.

- **Command Channel**: 시나리오 시작/중지/재시작, 설정 변경
- **Telemetry Channel**: pps, tx bytes, rx bytes, 응답 플래그, 세션 상태
- **Rule Channel**: PASS/FAIL 판정 조건 전달

물리적으로는 다섯 구간으로 나뉜다. 스키마는 `proto/dataplane.proto` 하나가
두 hop(③④)을 모두 정의한다.

| # | 구간 | 방식 | 핵심 |
|---|---|---|---|
| ① | worker lcore → 제어 스레드 | per-lcore 카운터 | 캐시라인 정렬 필수. 단일 writer 라 락·원자연산 불필요 |
| ② | worker lcore → 제어 스레드 | `rte_ring` (lock-free MPSC) | full 이면 **버리고** drop 카운터만 증가. worker 는 절대 블로킹 안 함 |
| ③ | C ⇄ 사이드카 (같은 장비, 공유 볼륨) | unix socket + protobuf-c | 4바이트 length-prefix. 네트워크가 아니라 재연결·백프레셔 문제가 거의 없다 |
| ④ | 사이드카 ⇄ 제어부 (장비 경계를 넘을 수 있다) | **gRPC** 스트리밍 + **mTLS** | 함대 설정의 주소 집합에 자동 연결/해제 |
| ⑤ | 벌크 데이터 | 공유 볼륨 (PV) | PCAP 은 GB 단위 → **경로 문자열만** 전달 |

**개별 패킷(mbuf)은 프로세스 경계를 넘지 않는다.** 148 Mpps 를 밖으로 내보내는
건 성립하지 않으므로 C 가 판정 결과와 요약만 만든다. µs 단위 반응(ACK 생략,
SYN-ACK 즉시 판정)은 전부 worker lcore 안에서 끝나므로, ③④가 지연되거나 끊겨도
판정 정확도에 영향이 없다.

**gRPC 를 C 에 직접 넣지 않는 이유는 성능이 아니라 격리다.** 이 채널의 부하는
텔레메트리 10 msg/s, 이벤트 상한 10k/s 로 gRPC 용량 대비 3~4자릿수 여유다.
C 프로세스에 gRPC 스레드 풀이 생기면 컨테이너 cpuset(= worker 코어 포함)을 떠돌며
busy-poll 루프를 선점할 수 있는데, 사이드카는 별도 컨테이너라 애초에 worker 코어에
올라갈 물리적 경로가 없다. 규약이 아니라 구조로 막는 쪽을 택했다.
부수적으로 C 데이터플레인이 순수 C 로 남는다(libstdc++·abseil·BoringSSL 불필요).

### 4-2-5. 설계상 핵심 결정
1. **Stateless 모드**는 100G급 전송에 최적화하고, **Stateful 모드**는 실제 세션/프로토콜 제어에 집중한다.
2. **TLS/HTTP는 Stateful 모드에서만 지원**한다.
3. **실시간 판정은 C에서 수행**하고, **세션 단위 판정은 Go에서 수행**한다.
4. **GUI는 브라우저 기반**으로 하되, 실행 파일 하나로 배포되도록 Go 내장 서버를 사용한다.

## 4-1. 실행 환경 & 데이터플레인 백엔드 (베어메탈 + 클라우드)

**목표**: 코드 한 벌로 베어메탈과 3대 클라우드에서 **모두 100G급 성능**. 환경에 따라 DPDK PMD(드라이버)를 갈아끼우는 **백엔드 추상화 계층**으로 구현. 실행 시 환경을 감지해 가능한 기능만 UI에 활성화.

**환경별 100G 달성 방법 (조사 근거 반영)**

| 환경 | 100G 달성 | DPDK PMD | 필수 요건 |
|---|---|---|---|
| 베어메탈 | 물리 NIC line rate | **Intel PMD** (100G E810=ice, 40G XL710=i40e) | hugepage, 코어 핀닝, NUMA |
| **AWS** | ENA 최대 100Gbps (EFA 조합 시 그 이상) | ENA PMD (DPDK 20.11+) | C6in 등 대형 인스턴스, SR-IOV |
| **Azure** | MANA 최대 **200Gbps** | MANA PMD (netvsc direct-to-vf) | **커널 6.14+** (Ubuntu 26.04 커널 7.0으로 충족), 가속 네트워킹 |
| **GCP** | Tier_1 최대 100/200Gbps | GVE PMD (DPDK 22.11+) | gVNIC, N2/C2 30+vCPU (200G는 C3 44+vCPU) |
| 폴백(DPDK 불가) | 부분 커널 우회 | **AF_XDP** | DPDK 미지원 인스턴스 대비 |

**환경별 기능 능력 매트릭스** (성능과 별개로 클라우드가 정책상 막는 것)

| 기능 | 베어메탈 | AWS | Azure | GCP |
|---|:---:|:---:|:---:|:---:|
| L2 임의조작 (MAC/VLAN) | ✅ | ❌ | ❌ | ❌ |
| L3 src IP 스푸핑 | ✅ | ❌ | ❌ | ❌ |
| L4 커스텀 플래그/seq, handshake 제어 | ✅ | ✅ | ✅ | ✅ |
| 커스텀 L7 (HTTP/TLS) | ✅ | ✅ | ✅ | ✅ |
| 100G line rate | ✅ | ✅ | ✅(200G) | ✅ |

> **핵심 정리**: 100G 성능은 세 클라우드 모두 달성 가능(Azure는 200G까지). 단 **L2 조작·src IP 스푸핑은 클라우드 격리 정책상 어디서도 불가** — 성능 문제가 아니라 가상 네트워크 설계 때문. 또한 100G+ 인스턴스는 시간당 비용이 크므로 테스트 시간 관리 필요.

### 4-1-1. 데이터 경로 3-tier (커널 우회 정도)

위 표가 **실행 환경** 축이라면, 여기는 그와 직교하는 **데이터 경로** 축이다.
"DPDK 를 안 쓸 수 있는가"의 답은 **DPDK 를 걷어내는 게 아니라 PMD 를 커널 경로로
바꾸는 것**이다 — `rte_ethdev` API 가 동일하므로 **데이터플레인 코드는 한 줄도
바뀌지 않고** EAL 인자만 달라진다.

```
Tier 1  -a 0000:43:00.0                      ← NIC 을 vfio 로 독점
Tier 2  --vdev net_af_xdp0,iface=eth2        ← NIC 은 커널이 계속 소유
Tier 3  --vdev net_af_packet0,iface=eth2     ← 준비물 사실상 없음
```

| Tier | 백엔드 | 도달 가능 속도 | 필요한 준비 | 검증기 현재 |
|---|---|---|---|---|
| **1** | DPDK + **vfio-pci** | 100G급 | hugepage · IOMMU · 코어 격리 · **PF 독점** · 재부팅 | ✅ 검증기에서 동작 확인(2026-08-25) |
| **2** | DPDK + **af_xdp PMD** | 10G급 (zero-copy 시) | 커널 XDP + `libbpf`/`libxdp`, 드라이버 ZC 지원 | ⚠️ 커널은 `CONFIG_XDP_SOCKETS=y` 인데 `libxdp` 부재로 **PMD 미빌드** |
| **3** | DPDK + **af_packet PMD** | 1G급 | 사실상 없음 (`CAP_NET_RAW`) | ✅ `librte_net_af_packet.so` **빌드됨** |

Tier 3 은 EAL `--no-huge` 와 조합하면 **hugepage 예약도 IOMMU 도 재부팅도 없이**
기동한다. af_packet 은 DMA 를 쓰지 않으므로 `--no-huge` 의 물리 연속성 제약에
걸리지 않는다. 1G 라인레이트가 1.49 Mpps 인 것과 맞물려, **1G 구성은 Tier 3 으로도
사정권**이다(코어당 처리량은 실측 필요 — af_packet 은 통상 1 Mpps 안팎).

> **Tier 2 를 막는 것은 커널이 아니라 배포판이었다.** 검증기 커널은 XDP 소켓을
> 지원하지만 이전 Ubuntu 20.04 에 `libxdp-dev` 가 없어 PMD 가 빌드되지 않았다.
> 26.04 재설치로 이 제약은 사라졌을 가능성이 높으나 **아직 확인하지 않았다** —
> Tier 1(vfio)이 정본이라 우선순위가 낮다. 7절 Open Issue 2 의 **OS 하한선**을
> 뒷받침하는 사례로 남겨 둔다.

**⚠️ Tier 2·3 의 치명적 제약 — 커널 간섭**

성능보다 이쪽이 본질이다. Tier 2·3 은 **NIC 을 커널이 계속 소유**하므로 커널 TCP
스택이 같은 패킷을 본다. 이 프로젝트의 핵심 기능인 handshake 제어를 하면:

```
Mir: SYN 송신 → 대상: SYN-ACK 응답 → 커널: "내가 모르는 세션" → RST 송신 💥
```

**커널이 시나리오를 오염시킨다.** `nftables`/`iptables` 로 해당 흐름을 DROP 하는
우회가 필요하고, 이는 판정 정확도에 대한 부채로 남는다.

**vfio 가 NIC 을 통째로 빼앗는 것은 성능 때문만이 아니라 이 간섭을 원천 차단하기
위해서다.** Tier 1 이 정본인 이유이며, Tier 2·3 은 아래 용도로 한정한다.

| Tier 2·3 의 용도 | 이유 |
|---|---|
| Phase 2~5 기능 개발 (헤더 빌더 · PCAP 재현 · TLS) | 속도가 필요 없고, BIOS·재부팅 없이 반복 개발이 가능하다 |
| 손댈 수 없는 장비에서의 동작 확인 | vfio 바인딩이 불가능한 환경 |
| 클라우드 폴백 | DPDK PMD 미지원 인스턴스 (위 4-1 표의 폴백 행) |

포기하는 것: µs 단위 판정 정밀도(커널 netdev 계층 경유), 배타 코어·busy-poll 전제,
그리고 위의 커널 간섭 차단. **성능·handshake 정확도의 최종 검증은 반드시 Tier 1 에서** 한다.

> 부수 효과: `librte_net_pcap.so` 도 함께 빌드돼 있어 **PCAP 파일을 가상 포트로
> read/write** 할 수 있다. NIC 없이도 Phase 4-1 리플레이 엔진을 개발·회귀 테스트할
> 수 있다는 뜻이다.

## 5. 두 동작 모드 (물리적 제약으로 분리)

100G 고속 전송과 실제 TLS 세션은 동시에 line rate로 불가능(TLS는 암호 연산이 병목).
따라서 **하나의 프로그램, 두 개의 모드**로 설계한다. (상용 툴들도 동일한 구조)

| 모드 | 목적 | 상태 | 성능 | 레이어 |
|---|---|---|---|---|
| **A. Stateless 고속** | 대량 트래픽 생성, L2~L4 이상동작 | 무상태 | **100G line rate** | L2~L4 |
| **B. Stateful 세션** | 실제 TLS+HTTP, handshake 제어 | 세션 유지 | 훨씬 낮음 (세션 수 제한) | L2~L7 |

## 4-3. 배포 아키텍처

**Docker Compose 를 정본으로 한다.** 오케스트레이터(k8s/k3s)는 초기 설계였고
Phase 0 에서 매니페스트까지 작성했으나, 코드와 대조한 뒤 접었다.

| 형태 | 대상 | 오케스트레이션 | 개수·리소스 조정 |
|---|---|---|---|
| **D — Docker Compose** (정본) | 운영 배포, 다중 PF, **장비 여러 대** | 없음 (장비마다 compose) | compose 파일 + `.env` |
| **S — 단독 실행 (컨테이너 없음)** | 컨테이너조차 반입 불가한 장비 | systemd 또는 수동 실행 | unit 파일 + `taskset` |

호스트 준비(BIOS VT-d · 커널 cmdline · hugepage · vfio-pci 바인딩 · 코어 격리)는
**두 형태가 완전히 동일**하다. 4-3-1 의 "호스트" 행은 애초에 컨테이너가 대신해
주지 못하는 영역이다.

절차는 [DEPLOYMENT.md](DEPLOYMENT.md), S 형태는 4-3-5 절.

### 4-3-0. 왜 오케스트레이터를 쓰지 않는가

1. **스케줄러가 정할 것이 없다.** 데이터플레인 컨테이너는 PF 가 꽂힌 장비에서만
   돌 수 있다. 배치를 PCIe 슬롯이 이미 결정했으므로 스케줄링이라는 문제 자체가
   성립하지 않는다. k8s 는 워크로드가 노드 간 **교체 가능**할 때 값을 하는데,
   여기선 정의상 교체 불가능하다. **장비를 늘려도 달라지지 않는다** — 데이터플레인은
   share-nothing 이라(개별 패킷이 프로세스 경계를 넘지 않는다) 장비 추가는
   클러스터 구성이 아니라 독립 단위 추가다.
2. **CPU Manager 가 명시적 cpuset 보다 못하다.** `cpu: "5"` 는 kubelet 이 코어를
   골라 주는 방식이라 어느 코어를 받을지 실행 전에 알 수 없고, 무엇보다 kubelet 은
   `isolcpus` 를 모른다. 커널 cmdline 의 격리 집합과 kubelet 의 `reserved-cpus` 를
   **서로 다른 파일에서 손으로** 맞춰야 했고, 한쪽만 바꾸면 격리되지 않은 코어를
   조용히 받는다. 지금은 `isolcpus` 가 유일한 출처이고 compose 의 `cpuset` 이
   그 값을 그대로 쓴다(`40-verify-node.sh` 가 일치를 검사한다).
3. **device plugin 이 없던 문제를 만든다.** PF↔인스턴스 바인딩이 임의가 되어
   축소 시 어느 PF 가 빠질지 알 수 없었다. `MIR_DEVICE_SPEC=pci:<BDF>` 로 직접
   지정하면 고정되고, 이 경로는 `eal_args.c` 에 이미 1순위로 구현돼 있었다.

**컨테이너는 유지한다.** 컨테이너화의 목적이 성능이 아니라 **재현성**이기
때문이다 — 장비마다 툴체인이 갈리면 `-march` 를 낮은 쪽에 맞춰야 한다. 바꾼 것은
오케스트레이션 층 하나뿐이고 바이너리·채널 구조는 그대로다.

부수 효과: 제어부의 k8s 클라이언트 의존이 사라져 Go 직접 의존이 3개로 줄었고,
`internal/k8s`·RBAC·ServiceAccount·PV/PVC 표면이 통째로 없어졌다.

### 4-3-1. 계층 경계

| 계층 | 담당 | 컨테이너가 못 하는 일 |
|---|---|---|
| 호스트 | BIOS VT-d, 커널 cmdline, vfio-pci 바인딩, hugetlbfs | — |
| Compose | cpuset 고정, 장치 전달, 재시작 정책 | IOMMU·hugepage **생성** |
| 애플리케이션 | EAL 인자 조립, hugepage **소비 상한**, 포트 구성 | — |

### 4-3-2. 핵심 결정

1. **PF 전체를 vfio-pci 로 패스스루**한다. VF 는 PF 의 spoof check / MAC 필터에
   막혀 L2 임의조작·src IP 스푸핑이 불가능한데, 그건 이 프로젝트의 핵심 기능이다.
   PF 는 netdev 가 아니라 문자 장치(`/dev/vfio/N`)이므로 compose 의 `devices:` 로
   그대로 넘긴다.
2. **코어 배치는 컨테이너 분리로 보장한다.** `dataplane` 은 `cpuset` 으로 격리
   코어에 고정하고, `agent` 는 `cpuset` 없이 공유 풀에 남긴다. 두 컨테이너가
   분리돼 있으므로 사이드카의 gRPC 스레드가 busy-poll 코어에 올라갈 물리적
   경로가 없다 — 규약이 아니라 구조로 막는다.
3. **메모리 상한을 애플리케이션이 건다.** 오케스트레이터가 걸어 주던 인스턴스별
   hugepage 한도(`hugepages-1Gi: 4Gi`)의 대응물이 compose 에는 없다. `MIR_MEM_MB` 를
   읽어 EAL 의 `--socket-mem`/`--socket-limit` 으로 직접 건다. **없으면 먼저 뜬
   인스턴스가 호스트 hugepage 를 전부 가져가고 나머지가 기동에 실패한다.**
   `--socket-mem` 은 기동 시 선확보라 부족분이 폴트 시점 SIGBUS 가 아니라 즉시
   기동 실패로 드러난다(fail-fast 가 상한의 핵심이다).
   NUMA 노드는 `/sys` 에서 읽어 **우리 cpuset 이 걸친 소켓에만** 배정한다 —
   Topology Manager `single-numa-node` 가 하던 정렬을 대신한다.
4. **비특권 실행.** vfio-pci + IOMMU 면 `IPC_LOCK`(+`SYS_NICE`)만으로 동작한다.
   VT-d 를 못 켜는 경우에만 no-IOMMU 폴백 + `privileged: true` 로 분기하며,
   그 대가(임의 물리 메모리 DMA 가능 → 격리 경계 소멸)를 문서에 명시한다.
5. **제어 채널은 mTLS.** 사이드카 포트가 장비 밖으로 열리므로 여기 닿는 누구나
   라인레이트 송신을 시킬 수 있다. 평문은 `MIR_INSECURE=1` 을 명시해야만 켜지고,
   인증서 설정과 함께 주면 기동을 거부한다("보안을 켰다고 믿는데 평문"이 가장
   나쁜 결과라 의도적으로 막는다).

### 4-3-3. 개수·리소스 조정

GUI 에서 조정할 수 있어야 한다는 요구가 있었으나, **제어부는 라이프사이클을
조종하지 않는다**로 정리한다. 근거 둘:

- **권한.** compose 를 조종하려면 장비마다 `docker.sock`(root 등가)을 받아야
  한다. GUI 가 웹으로 노출되는 구조에서 명백한 후퇴다. 오케스트레이터 시절에는
  RBAC 으로 좁힌 위임이 가능해 이 API 가 **쌌기 때문에** 존재했던 것이지
  필요해서 생긴 게 아니다.
- **멀티 장비.** `docker.sock` 은 장비 로컬이고 제어부는 원격이므로 애초에
  성립하지 않는다.

그리고 **"무중단 변경"은 어차피 달성 불가능**하다:

1. 컨테이너 spec 은 불변 → 변경 = 재생성
2. hugepage·확장 리소스는 in-place resize 대상이 아니다
3. **DPDK 가 런타임 lcore 변경을 지원하지 않는다** — `rte_eal_init` 이 lcore 집합을
   프로세스 생존 기간 동안 고정한다

어떤 방식이든 재시작을 수반하므로 **선언적 파일이 맞는 자리**다.

| 요구 | 실현 |
|---|---|
| 개수 변경 | `.env` 의 `COMPOSE_PROFILES` + `docker compose up -d` |
| CPU/메모리 변경 | `.env` 의 `MIR_DP*_CPUSET` / `MIR_MEM_MB` + 재생성 |
| 개별 재시작 | `docker compose restart <svc>` |
| 크래시 복구 | `restart: unless-stopped` (자동) |

제어부가 하는 일은 **관측**이다. 그리고 이쪽이 오히려 정확해졌다 —
함대 설정(기대)과 `HelloResponse`(실측)를 따로 들고 대조하므로
`unreachable` / `no-ports` / `pf-mismatch` 가 구분된다. 노드 allocatable 합산으로는
"몇 개가 Ready 인가"밖에 알 수 없었다.

### 4-3-4. 멀티 장비

장비 2대 이상을 한 제어부가 묶어 구동하는 것이 **확정 요구**다. 데이터플레인이
share-nothing 이라 장비 추가 자체는 싸지만, 장비 경계를 넘으면서 새로 생기는
문제가 셋 있고 **이들은 오케스트레이터 선택과 무관**하다.

1. **인증** — 4-3-2 의 5번. mTLS.
2. **시계 동기** — `TelemetrySnapshot.ts_ns` 가 `CLOCK_REALTIME` 이라 장비 간
   시계가 어긋나면 상관 분석과 지연 측정이 무의미해진다. PTP(ptp4l + phc2sys)가
   전제이고 X710·E810 모두 하드웨어 타임스탬핑을 지원한다.
   → [deploy/host/60-ptp.md](../deploy/host/60-ptp.md). **허용 오차는 미확정**
   (판정 규칙이 정해져야 산출된다 → 7절).
3. **조율된 시작** — `StartScenarioRequest.start_at_ns` 로 공통 시각을 지정한다.
   2번에 의존하며, 송신 엔진(Phase 2)과 함께 구현한다. 지금은 proto 에 필드
   자리만 잡혀 있다.

기대 인벤토리는 `fleet.yaml` 이 단일 출처다. 인스턴스 이름은
`<machine>-dp<id>` 로 만들어지고 compose 의 `HOSTNAME` 과 반드시 같아야 한다 —
그 값이 EAL `--file-prefix` 와 텔레메트리 `node_id` 로 쓰이므로, 어긋나면 설정상의
인스턴스와 보고해 오는 인스턴스를 이어 붙일 수 없다.

### 4-3-4-1. 클라우드 이식성

4-1 절의 "백엔드 추상화" 원칙을 배포 층에 적용한다. 환경마다 달라지는 것을
**hugepage 크기 · 특권 여부 · 장치 지정 방식** 셋으로 한정한다.

- **AWS/GCP**: 같은 vfio-pci 모델 → 그대로 재사용 가능. 단 IOMMU 지원
  인스턴스는 `*.metal` 계열뿐이라 그 외에는 특권 실행이 강제된다
- **Azure**: 모델이 다르다. netvsc + bifurcated 드라이버 구조이고, MANA PMD 는
  BDF 가 아니라 **MAC 주소**로 바인딩 대상을 정한다 → `eal_args.h` 의
  `DEVICE_SPEC_MAC_ADDR` 경로를 미리 열어 둔 이유
- **1GB hugepage 는 부팅 시에만 예약 가능**한데 managed 노드는 cmdline 접근이
  막히므로 2MB 로 내려야 한다
- **권고**: 성능 검증 환경은 `*.metal` 로 통일한다. 일반 인스턴스는 기능 테스트용

### 4-3-5. 단독 실행 형태 (S) — 컨테이너 없이 장비 안에서

**왜 필요한가**

- 이미지 빌드 한 번이 수 분(DPDK 를 소스에서 빌드)이라 반복 주기가 길다.
  Phase 1~5 의 실제 작업은 NIC 한 장과 바이너리 두 개면 대부분 끝난다.
- 반입 대상 장비에 컨테이너 런타임을 올릴 수 없는 경우가 있다(정책·자원).
- 장애를 **컨테이너 계층의 문제와 DPDK 계층의 문제로 분리**해 좁힐 수 있다.

**구성**

```text
[React + TypeScript GUI]
        │ WebSocket / REST
        ▼
[mir-control (Go)]  — 시나리오·규칙·집계 + 로컬 프로세스 관리
        │ ③ unix socket (사이드카 없음 — ④ gRPC 홉이 통째로 빠진다)
        ▼
[mir-dataplane (C/DPDK)] × N   ← NIC PF 하나당 프로세스 하나
```

**최종 목표는 사이드카(mir-agent) 없이 제어부가 hop ③ 에 직접 붙는 것이다.**
사이드카의 존재 이유는 gRPC 스레드가 busy-poll 코어를 침범하지 못하도록 **구조로**
막는 것인데(4-2-4), 단독 실행에서도 제어부는 이미 별도 프로세스이고 `isolcpus`+cpuset
으로 worker 코어 밖에 고정되므로 같은 보장이 성립한다. 별도 컨테이너라는 장치가 없을 뿐
격리의 근거는 그대로다.

- **대가**: 제어부가 데이터플레인에 붙는 경로를 둘 갖게 된다(직결 / gRPC).
- **대안**: 단독 실행에서도 사이드카를 그대로 띄우면 경로는 하나로 유지되지만,
  **격리 이득 없이** 프로세스와 홉이 하나씩 늘고 디버깅 시 볼 곳만 많아진다.
- **선택**: 최종적으로는 경로 분기. 분기 지점을 `registry` 한 곳으로 좁히고, hop ③
  프레이밍 구현(`control/internal/ipc`)은 사이드카와 공유한다 — 새로 만드는 코드가 아니다.

> **단, 당분간은 사이드카를 그대로 띄운다.** 제어부의 직결 경로는 `registry` 백엔드
> 분기와 함께 들어가야 하는데 그 작업이 아직 없고, 사이드카는 코드 변경 없이 로컬
> gRPC(`127.0.0.1:910N`)로 바로 뜬다. 즉 **현 시점의 S 형태 = 데이터플레인 + 사이드카**
> 이고 제어부는 아직 붙지 않는다. 설치 절차와 그 제약은
> [INSTALL-STANDALONE.md](INSTALL-STANDALONE.md), 특히 7절.

**컨테이너가 해주던 일의 대체**

| Compose 가 하던 것 | 단독 실행에서 |
|---|---|
| 배타 코어 할당 (CPU Manager `static`) | 커널 `isolcpus` + 프로세스별 cpuset/taskset. 데이터플레인은 격리 코어에, 제어부는 그 **밖**에 고정한다 |
| NIC PF 할당 (SR-IOV Device Plugin) | `MIR_DEVICE_SPEC=pci:<BDF>` 로 직접 지정 — **이미 구현됨**(`eal_args.h`) |
| hugepage 할당량 | EAL 인자 + 프로세스별 `--file-prefix` 로 충돌 방지 — **이미 구현됨** |
| 재시작·개수 조정 | systemd 템플릿 유닛(`mir-dataplane@<BDF>.service`). **수동 실행 경로를 반드시 유지**한다 |
| PCAP 공유 볼륨(PV) | 로컬 디렉터리. ⑤ 채널은 애초에 **경로 문자열만** 전달하므로 코드가 바뀌지 않는다 |
| 인스턴스 디스커버리 | 함대 설정 대신 소켓 경로 규약 (`/var/run/mir/dp-<n>.sock`) |

**바뀌지 않는 것** — 이 절의 핵심은 여기다.

- 데이터플레인은 **NIC PF 하나당 프로세스 하나**. 한 프로세스가 여러 PF 를 잡는
  구조로 가지 않는다 — `rte_eal_init` 이 lcore 집합을 프로세스 단위로 고정하므로
  PF 별로 코어를 조정할 방법이 사라진다.
- 그 고정 때문에 **개수·리소스 조정의 무중단은 여전히 불가능**하다(4-3-3 의 제약 3).
  재시작 범위를 데이터플레인으로만 한정한다는 목표도 동일하다.
- 채널 ①②③⑤ 와 스키마(`proto/dataplane.proto`)는 그대로다. 빠지는 것은 ④ 하나.
- **"monolithic" 은 단일 프로세스를 뜻하지 않는다.** Go 제어부와 C 데이터플레인을
  한 프로세스로 합치려면 cgo 로 DPDK 를 불러야 하는데, 그 오버헤드와 스레드 모델
  충돌이 B안 채택의 전제(4절)를 무너뜨린다. 합쳐지는 것은 **배포 단위**이지
  프로세스가 아니다.

## 6. 현실적 개발 로드맵 (단계별)

B안은 큰 프로젝트라 **작동하는 결과물을 단계마다** 만드는 순서로 갑니다.

> 각 Phase 가 **어느 파일·어느 채널을 건드리는지**의 매핑은
> [ARCHITECTURE.md 6절](ARCHITECTURE.md)에 있다.

- **Phase 0 — 환경/하드웨어 확정**: NIC 모델·DPDK PMD 확인, hugepage/CPU 코어 세팅
  + **컨테이너/Compose 인프라 골격** (4-3 절). *골격 작성 완료, 실물 검증 대기*
  + **단독 실행 형태(S)** — systemd 유닛과 제어부의 로컬 프로세스 관리 경로.
    *미착수*. Phase 1~5 의 개발·검증은 이 형태를 기본으로 쓴다(반복 주기가 짧다).
- **Phase 1 — DPDK "hello packet"**: 단일 커스텀 패킷 1개 송신 성공 (파이프라인 검증)
- **Phase 2 — L2~L4 커스텀 + 고속 송신**: 헤더 빌더 + 멀티코어 폭풍 전송, pps 측정
- **Phase 3 — 수신 캡처 + 판정 엔진**: 응답 스니핑, 규칙 판정, 기본 리포트
- **Phase 4 — 커스텀 handshake 제어**: ACK 생략 등 stateful lite (핵심 기능)
- **Phase 5 — TLS + HTTP stateful 모드**: 실제 세션 수립 + 커스텀 페이로드
- **Phase 6 — GUI**: React Flow 시나리오 빌더 + 송신 카운터 / 실시간 패킷 로그 / 세션 판정 3영역
- **Phase 7 — 400G 튜닝**: 코어 스케일링, 배치, NUMA/캐시 최적화 (베어메탈 기준).
  **목표기 도입이 전제**다 — 검증기(40G)로는 착수할 수 없고, 장비 세팅 시 OS 버전
  확정부터 시작한다. 착수 조건과 체크리스트는 7절 Open Issue 2 ③.
- **Phase 8 — 클라우드 백엔드 이식**: 백엔드 추상화 위에 **AWS(ENA) → Azure(MANA) → GCP(GVE) 순서**로 PMD 추가 + 환경 자동 감지 + AF_XDP 폴백 + 클라우드별 100G 튜닝

   | **meson** | **1.4 이상** | 1.10 ✅(이미지) | DPDK 25.11 최소 요구는 0.57.2 지만, 배포판 패키지(20.04 는 0.53.2)로는 부족해 pip 설치가 강제됐다. 배포판 패키지로 충족되는 OS 를 고르는 편이 재현성에 유리하다 |

   | **지원 기한** | 도입 시점 기준 **표준 지원 3년 이상 잔여** | 26.04 LTS ✅ | 이전 검증기는 EOL 배포판이라 보안 업데이트 경로가 없었다 |

   > 나을 수 있어 **확정은 장비 세팅 시점으로 미룬다.**

## 8. 설계 단계 결론

현재 초안 기준으로 프로젝트는 다음 방향으로 확정하는 것이 적절하다.

- **핵심 목표**: L2~L4는 무상태·고속 모드로 100G급 전송, L7는 stateful 세션 모드로 실제 프로토콜 검증
- **구현 전략**: C 데이터플레인 + Go 제어부 + React GUI의 3계층 구조
- **개발 우선순위**: DPDK hello packet → L2~L4 송신 → 수신/판정 → handshake 제어 → TLS/HTTP
- **운영 제약**: 클라우드에서는 L2 임의조작·src IP 스푸핑이 불가하므로, 기능 범위는 환경별로 분기해야 한다.
